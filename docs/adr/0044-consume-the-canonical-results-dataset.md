# Consume the canonical results dataset; retire the legacy model

Election *results* — mayoral and councillor vote counts, winners, and incumbency — are now sourced from the external **canonical dataset** (`toronto-election-results`, `data/out/toronto_election_results.csv`: one row per candidate per contest, ward-level, `office ∈ {mayor, councillor}`, 2003–2025, with persistent fuzzy-matched `candidate_id` c00XXX, votes, `total_contest_votes`, `vote_share`, `elected`, `acclaimed`, `incumbent`, `ward_system`). This repo **no longer pulls or processes election results of its own** — it vendors that dataset and reads from it. The build-your-own-results pipeline, and with it the entire legacy Monte-Carlo forecast model, is retired.

This decision follows from three judgments the maintainer made explicit: **backwards compatibility is an anti-priority** (retire anything to-be-retired now); the canonical dataset is the single source of truth for results; and the current rebuild — the qualified Mayoral Endpoint Bridge (ADR 0030/0042), the M3 publication layer, the cross-city incumbency trials (ADR 0013/0039), and the descriptive Council race cards (ADR 0043) — already supersedes the legacy model in full. The legacy pipeline (`run.py` → `forecast.py`/`mayoral.py`/`council.py`/`snapshot.py`, with `simulation.py`, `coattails.py`, `pool.py`, `aggregator.py`, `lean.py`, plus the descriptive-estimate layer `polling_estimate.py`/`ward_polling.py` and the `process_all.py`/`build_snapshot.py`/`fetch_elections.py` tooling) is deleted, not deprecated.

**The dataset is share-identical to the retired sources.** Before repointing, the canonical mayoral outcomes were confirmed vote/share/winner byte-identical to the old sidecar+ward-aggregation outcomes for every cycle (all 355 rows diff to zero once `candidate_id` is ignored). The council biographies were repointed onto `office=councillor` keyed on the persistent `candidate_id`. So the substantive inputs to the forecast did not change; only their provenance did.

**One genuine subtlety — candidate identity, not vote data.** The canonical stores names First-Last (`Giorgio Mammoliti`) where the retired city workbooks used Last-First (`Mammoliti Giorgio`). The model derives a synthetic id for minor (never-named-by-a-poll) candidates by slugifying the name, so those ids legitimately change string form (`toronto_2003:andrews-don` → `toronto_2003:don-andrews`). This matters in two places, both resolved:

- **Named-candidate linkage.** Poll↔outcome linkage for major candidates runs through a curated name→id map (`_KNOWN_CANDIDATE_IDS`), which is order-robust; only Chloe Brown needed a canonical name form added (`Chloe-Marie Brown`), without which 2022 lost all eligible poll readings.
- **Polled-minor linkage.** Seven namespaced minors who *ran and were polled* (Faith Goldy 2018; Mammoliti, Perruzza, Saccoccia, Caesar-Chavannes, D'Angelo, Davis 2023) broke the `candidate_field ⊆ final_ids` eligibility check when their outcome id flipped form (2023 eligible poll samples fell 20→8). The historical poll bundle already stored each candidate's name in canonical First-Last form, so the fix was to regenerate those seven derived join-keys from their own name — which also repaired a latent id-vs-name ordering inconsistency in the poll file. Coverage returned to identical.

**Byte-identical qualification metrics are provably unreachable, and that is acceptable.** The endpoint's Monte-Carlo seed is `sha256(sorted(zip(candidate_ids, shares)))` — deterministic, but a function of the id *strings*. Restoring the old outcomes reproduces the pre-integration scores to eight decimals, proving the model is deterministic and the only changed input is the cosmetic minor-candidate id form. Since the canonical's First-Last names are the source of truth, the seed necessarily reshuffles, yielding a different-but-equally-valid realization. The **achievable and accepted standard** is therefore: *identical share inputs, identical poll coverage, identical qualification verdict, with metrics differing only by the seeded-MC reshuffle*. On that standard the bridge still **qualifies** — relative arm passes (4/6 cycles), all three reliability gates clear their frozen maxima (winner log 0.1135, close Brier 0.0520, share CRPS 0.0043 ≤ 0.2410/0.0746/0.0050), margin CRPS 0.0352 beats the comparator. Chasing byte-identical scores by contorting the canonical ids back to legacy forms would reintroduce exactly the coupling being removed.

**Deferred: adopt the canonical persistent `candidate_id` (c00XXX) as the poll↔outcome join key.** The name-order fragility above is a symptom of joining on derived slugs. The canonical already carries a persistent, fuzzy-matched candidate id across cycles; re-keying the historical poll responses and the endpoint join onto it would make this class of breakage impossible forever. It is a larger change (poll-response re-keying, endpoint join logic, possible frontend ripple) and is deferred to the roadmap, not done here. Until then, the curated name map plus regenerated join-keys hold the linkage.

**Kept, per the maintainer's D4.** The cross-city incumbency trials (`mayoral_incumbency_trials.csv`, ADR 0013/0039) and the ballot-timing election manifest (`mayoral_elections.csv` — nomination-close and Final-Ballot dates, ADR 0002) are *not* results and stay in this repo; they are original editorial/temporal data the canonical dataset does not carry. The poll-ingestion tooling that maintains the endpoint's own poll corpus is likewise kept.

**Consequence for publication.** The frontend's `model_snapshot.json` / `polls_snapshot.json` were produced only by the retired `build_snapshot.py`; the committed JSONs are left in place (they go stale) until the M3 publication layer is wired to an emitter (the INT milestone). This is the already-accepted state of a mid-flight rebuild that is not authorised to publish until the Final Ballot is set (ADR 0002).
