# Council candidate historical-hint flags

The Council v1 race card (ADR 0043) gains a per-candidate **historical-hint** signal: for each 2026 registered councillor candidate, which of the `defeatability-index` catalog's supported hints trigger, attached with the catalog's ready `frontend_copy`, effect estimate, and evidence tier. These are **historical frontend context only — never predictions, causal effects, or model inputs** — and sit alongside the existing exposure triggers and competitiveness facts as another strictly non-predictive cue.

**The hint definitions are consumed, not reinvented.** The six supported hints and their exact trigger conditions, plus the computation rules (history scope, signed-margin rule, elected/acclamation rule, continuous-display rule, display copy), come from the sibling analysis and are vendored into `data/raw/hints/` (`supported_historical_hints.csv` + `historical_hint_contract.json`) by `scripts/sync_historical_hints.py`, re-synced when the analysis is refreshed. This repo computes only the **2026 per-candidate features** (the historical frame is 2003–2025, so the live field is not in it) following that contract, and fires the hints from the catalog's own `trigger_field`/`trigger_operator` — so a change to the catalog flows through without code edits, and the firing cannot silently drift from the measured associations.

**Identity: a deliberate, maintainer-chosen divergence from the contract.** The contract's first rule is "use the persistent `person_id`; never match by name." That rule protects the *analysis* — a mis-identification would corrupt the association estimates. But the live 2026 field is not in the canonical and carries no `person_id` (`councillor_registered.csv` is ward + names only), so on this side some name bridge is unavoidable. The chosen resolution, more generous than upstream by explicit instruction: a registration resolves to a **single upstream `person_id`** by a token-set match that tolerates accents, word order, and middle names, across *all* offices — but its history is then exactly the candidacies upstream linked to that `person_id`. We do **not** re-discover a person by sweeping same-named candidacies (which would merge people upstream deliberately kept apart and pull in `person_id`-blank rows), and a name that resolves to two different `person_id`s is left unmatched rather than guessed. The accepted trade-off is a possible false-positive link to a same-named person; for a non-predictive context cue that is low-stakes, and the failure mode is dominated by *under*-matching (ambiguous → no flag), not over-matching. This generosity is why a candidate whose only prior office was trustee, MPP, MP, or mayor — invisible to the councillor-only biography match — still gets flags (e.g. former MP Ted Opitz, four-term trustee Joseph Martino).

**History scope follows the contract exactly.** Non-council offices are mayor, MP, MPP, and trustee; "council" is councillor only. A Returning councillor (a prior councillor winner who is not the ward's sitting incumbent) has their council record count toward the combined elected-office measures; a **sitting incumbent's prior council record is excluded** (verified: ward-11 incumbent Dianne Saxe's 2022 council win is correctly dropped, leaving only her MPP result). Wins include acclamations; margins are signed vote-share, negative for losses, null for an acclamation with no runner-up; continuous hints fire only when their value is non-null (a candidate who ran but never won fires a victory count of zero).

**Consequence.** The council race-card schema is bumped to v2 with a `historical_hints` array per candidate. The change is additive and descriptive; it touches no forecast, no gate, and no model input, and the Council card remains outside the qualification ladder (ADR 0043).

**Amended by ticket 02 (council-signal-explanations).** The catalog's static `frontend_copy` is no longer the display contract. Each fired hint now additionally carries a signed **direction** (`positive`/`negative`) and **structured provenance**, both additive within the current schema (no version bump; existing consumers ignore the new fields). The direction is derived from the candidate's *actual value and* the measured association, not the coefficient alone — a negative most-recent margin or a measured-zero victory count reads `negative` even though those associations' coefficients are positive; opponent-history signals are `negative` for the subject. The provenance carries the subject (own/opponent), the source candidate name for opponent signals, the concrete source race (office type, year, district, result, placement rank, field size, signed margin), the victory count and qualifying-candidacy count for the count hint, and a `coverage` state that distinguishes a **measured zero** from missing history. The frontend composes each explanation from this provenance instead of printing `frontend_copy` (retained only as a raw fallback), so the display cannot silently drift back to generic catalog prose. The firing rules, thresholds, measured associations, and evidence gates are unchanged — this is a presentation-provenance addition, still strictly non-predictive.
